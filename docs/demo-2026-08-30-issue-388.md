## What this proves

- The Select → Dispatch → Coder → Verify → (Analyser → retry)* → Ship
  loop runs for real against a real GitHub issue, with a real LLM, a
  real `pytest` verification pass, and a **real PR opened at the end**
  — see [Run C](#run-c--the-full-loop-working-end-to-end-including-ship).
- The retry loop is bounded (`max_revisions=3`, visible directly in the
  log lines below) and the Analyser's feedback is genuinely fed into the
  next Coder attempt — see [Run A](#run-a--three-bounded-attempts-genuine-analyser-feedback).
- Per-run LLM cost tracking works and is visible in both the
  per-run and per-pass log lines.
- A real gap *was* found mid-exercise — the Ship step failed on a
  pinned dependency version — root-caused, fixed, merged, and
  **re-verified with a real opened PR** before this write-up was
  finalized. Nothing here is presented as working that wasn't actually
  re-run and confirmed after the fix.
- Reviewing that real PR (#394) surfaced a second, independent gap: its
  AI-drafted description was a raw placeholder template, because the
  underlying tooling can only draft a PR body via a *local*
  Ollama/LM Studio server, with no cloud-provider path at all — so any
  cloud-mode dispatch silently gets the placeholder. That gap was fixed
  upstream in [cicaid](https://github.com/leonarduk/cicaid) (the free
  devtools CLI both issue-worm and issue-worm-pro build on).

## Setup

- Fresh clean-environment install of issue-worm-pro.
- `CODER_MODEL_SOURCE=cloud`, `ANALYSER_MODEL_SOURCE=cloud`,
  `DEEPSEEK_API_KEY` set, `CODER_TARGETS=cloud:api.deepseek.com:deepseek-v4-flash`.
- The task: implement a `duration.py` parser against a pre-existing
  spec-as-tests file that includes a compound-format edge case
  (`"1h30m"` → 5400s) — chosen to be the kind of thing a first LLM

  failure — the retries in Run A came from an unrelated
  workspace-hygiene issue, described honestly below rather than dressed
  up as something it wasn't.

### What that turned out to be (and how it was fixed)

The Scheduler's Ship step calls `cicaid commit-and-push --model-source
cloud`. The first hypothesis was that the pro devtools extension had
dropped `commit-and-push` entirely in favour of a new, Ollama-only
`publish-pr` command — and a first fix attempt worked around that by
bypassing `cicaid` and calling `commit-and-push` directly. That fix was
correctly rejected: bypassing `cicaid`'s dispatcher defeats the actual
point of its design.

The real root cause, found by reading `cicaid`'s dispatcher source
directly: it already has exactly the extension mechanism this needed —
it discovers extension-provided commands dynamically via
`importlib.metadata.entry_points(group="cicaid.commands")`, specifically
so it never needs a new release just because an extension adds a
command. The pro devtools extension *does* register `commit-and-push`
and `create-issue` under that exact group — starting at a specific patch
release. This deployment was pinned one patch release behind that fix,
so the dispatcher genuinely had no way to discover those commands. It
was a stale dependency pin, not a missing feature or a design gap. Fixed
by bumping the pin — zero code changes to the scheduler needed.

## Narration script

Suggested order and talking points if walking through this live from
this document instead of a live terminal:

1. **Open with Run C.** "One command, `issue-worm build`, took a real
   GitHub issue to a real, merged-ready PR in under a minute — here's
   the PR." Point at `max_revisions=3` in the `run start` line — the
   bound is visible directly in the log, not just in the source — and
   at the `Marked PR ready for review` line with the real URL.
2. **Switch to Run A for the retry mechanic.** "Here's what it looks
   like when the Verifier fails — `coder attempt 1/3` → `verifier` →
   `analyser` → `coder attempt 2/3`. The Analyser isn't just relaying
   raw pytest output back — quote its `Assessment of the Approach`
   paragraph: it correctly identified that the actual code under test
   was fine and the *real* failures were elsewhere, exactly the
   translation step the Analyser exists to do instead of retrying
   blind." Be upfront that this particular run's failures were a
   workspace-hygiene artifact, not a code bug — say so before anyone
   asks.
3. **Point at the bound being real, not just configured.** "It stopped
   at attempt 3, not attempt 4 — `run end ... status=failed`, then a
   `needs-help` label and a comment with the failure detail, not an
   infinite loop."
4. **Cost tracking.** Point at `llm_calls=1 total_tokens=1086
   est_cost_usd=0.0011` on Run C vs `llm_calls=5 total_tokens=22576
   est_cost_usd=0.0226` on Run A's 3-attempt run, and the per-pass
   aggregate line right below each. "This is the answer to 'how do you
   watch cost' — it's not instrumented after the fact, it's in every
   run's own log line."
5. **Tell the Ship-step story.** "This exercise found a real bug — the
   Ship step was silently broken — root-caused it to a one-patch-behind
   dependency pin, rejected the first (wrong) fix because it missed the
   point of the extension design, fixed it properly, and re-ran the
   whole thing to confirm a real PR opens. That's the actual answer to
   'how do you know this works' — not code review, execution."
